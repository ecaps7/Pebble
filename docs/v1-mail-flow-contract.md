# 第一条邮件处理链：A/B 接口约定

状态：A 已确认的草案，待 B 核对。方法名均为暂定名。

依据：`v1-spec.md` 和 `v1-design.md` §10。本文件只细化第一条邮件链的交接接口。

## 1. 本次目标

用户从 PC 或手机网页发起邮件处理请求，Agent 查询邮件并生成回复草稿；用户审阅、编辑并明确确认后，由程序发送，保存实际结果并交回 Agent 向用户说明。

上述流程用于接口联调，不固化模型的业务决策；需要补充信息时，Agent 可以先追问用户。

## 2. 已有分工

| 负责人 | 职责 |
| --- | --- |
| A | Web 页面、Gateway、任务与草稿持久化、版本管理、确认与执行控制、进度及结果读取 |
| B | SDK 装配与会话恢复、工具注册、Gmail 查询与草稿准备、邮件业务校验、发送与结果核实、执行结果交回 Agent |

发送函数由 A 的 Confirmation 调用，不直接暴露给模型。

## 3. Gateway 向 Agent 提交用户消息

提供方：B。调用方：A 的 Gateway。调用形式：同一 Python 服务内的方法调用。

### 分工与输入

A 接收网页消息，为新任务创建并保存任务记录；B 负责创建或恢复 SDK 会话并启动 Agent。A 保存任务与 SDK 会话 ID 的对应关系。

| 输入字段 | 含义 |
| --- | --- |
| `task_id` | A 保存的任务 ID |
| `message` | 用户输入的原文 |
| `sdk_session_id` | 首次调用为 `None`；同一任务后续调用传入 A 已保存的 SDK 会话 ID |

### 事件返回方式

B 的入口以异步生成器形式边执行边返回事件，A 持续消费事件，保存必要信息并通过 SSE 向页面转发用户可见内容。

“本轮结束”仅表示 Agent 当前轮停止输出，不代表任务成功或邮件已发送；Agent 可能正在等待用户补充信息或确认草稿。发送结果以实际执行记录为准。

### 事件结构与结束规则

B 返回字典，通过 `type` 区分事件。

| 事件 | 示例 | A 的处理 |
| --- | --- | --- |
| 会话就绪 | `{"type": "session", "sdk_session_id": "s_001"}` | 保存任务与会话的关联 |
| 回复文本片段 | `{"type": "text", "text": "我找到了这封邀请。"}` | 按顺序追加显示到当前回复 |
| 本轮正常结束 | `{"type": "done"}` | 结束本轮进度展示 |
| 本轮运行失败 | `{"type": "error", "message": "Agent 服务连接失败"}` | 展示错误并结束本轮进度展示 |

- 创建或恢复会话后返回 `session`，随后再返回文本；若会话创建或恢复失败，则返回 `error`。
- `text` 可以返回多次，每次只包含新增文本。
- 一轮以 `done` 或 `error` 之一结束；`error` 后不再返回 `done`。
- 这些事件描述 Agent 本轮运行情况，不能替代邮件发送结果记录。

草稿展示通知由 A 发出，见第 7 节；不属于 B 的 Agent 事件。

## 4. 回复草稿保存

提供方：A。调用方：B 的准备回复工具。调用形式：同一 Python 服务内的方法调用，暂名 `save_reply_draft`。

### 分工

- B 生成回复内容并完成邮件业务校验，然后调用 A 的保存方法。
- A 统一持久化草稿，分配操作 ID 并管理版本。
- 保存成功后，B 才能向 Agent 报告草稿已准备好。
- 保存失败时明确返回失败，不得向 Agent 或用户报告草稿已保存。

`task_id` 标识整个任务；`operation_id` 标识其中一项待确认发送的回复，供后续读取、编辑和确认使用。

### 基础输入

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `task_id` | 所属任务 ID | 将草稿关联到任务 |
| `source_message_id` | 要回复的原邮件 ID | 明确回复对象，供去重使用 |
| `thread_id` | Gmail 邮件线程 ID | 关联原邮件所在的会话 |
| `to` | 收件人地址列表 | 展示给用户确认，供发送使用 |
| `subject` | 邮件主题 | 展示、编辑和发送 |
| `body` | 回复正文 | 展示、编辑和发送 |

`operation_id` 和 `version` 由 A 保存时生成，B 不传入。以上为基础业务字段；Gmail 回复所需的协议细节由 B 核对，尚不能据此认定发送接口已完整。

### 创建或找到已有操作的统一返回

`save_reply_draft` 首次创建和找到已有操作时，均返回 `operation_id`、`version`、`status`。状态含义见第 11 节。

首次保存成功：

```json
{
  "operation_id": "op_001",
  "version": 1,
  "status": "pending"
}
```

找到已有操作时返回其实际版本与状态，不覆盖内容、不触发重发。B 根据状态如实说明当前情况，不能把已发送的回复报告为新草稿。

### 重复准备与用户要求重写

- 重复准备：用户未要求修改，但 Agent 再次准备同一封来信的回复，或其他任务再次处理该来信。按 `source_message_id` 定位已有回复操作；存在时复用，不新建第二份，也不覆盖已有内容。首次准备负责创建或找到已有草稿。
- 用户要求重写：例如“这份回复太正式了，重新写得自然一点”。这是修改请求，Agent 通过编辑接口更新已有草稿，保留 `operation_id` 并生成新版本，供用户重新审阅确认。
- 用户手动编辑和 Agent 重写遵守同一套版本规则。原邮件 ID 用于定位回复操作，不能仅因 ID 相同就忽略明确的修改请求。

上述重写针对可编辑草稿，不改变设计中“执行中的内容不能原地修改”的约束。

## 5. 编辑回复草稿

提供方：A。调用方：接收页面编辑的 Gateway 或 B 的草稿编辑工具。内部方法暂名 `update_reply_draft`。

| 输入字段 | 含义 |
| --- | --- |
| `operation_id` | 要修改的草稿操作 ID |
| `expected_version` | 本次修改基于的草稿版本 |
| `to` | 修改后的完整收件人地址列表 |
| `subject` | 修改后的完整主题 |
| `body` | 修改后的完整正文 |

用户手动编辑和 Agent 重写共用此接口。A 调用 B 的邮件业务校验，校验通过后在保存时原子检查当前版本是否等于 `expected_version`；符合版本及可编辑状态要求才保存新版本。版本不匹配时拒绝本次保存，提示版本已变化，不覆盖当前内容。

示例：基于 `op_001` 第 1 版提交修改，保存成功后返回：

```json
{
  "operation_id": "op_001",
  "version": 2
}
```

新版本不能沿用旧版本的确认。

## 6. 邮件业务校验

提供方：B。内部方法暂名 `validate_reply_draft`。首次生成和后续编辑使用同一个校验方法。

| 输入字段 | 含义与来源 |
| --- | --- |
| `source_message_id`、`thread_id` | 原邮件及线程标识；编辑时由 A 从已有草稿读取 |
| `to`、`subject`、`body` | 本次准备保存的完整收件人、主题与正文 |

该方法检查邮件内容及回复关联是否符合发送要求，不保存、不发送，也不自动改写内容。

校验通过：

```json
{"valid": true, "errors": []}
```

校验不通过示例：

```json
{
  "valid": false,
  "errors": [
    {"field": "to", "message": "收件人地址格式不正确"}
  ]
}
```

校验不通过时不保存此次内容；编辑时由 A 将原因展示给用户或返回给 Agent。校验通过不等于已经发送，发送仍须经用户明确确认。

## 7. A 负责的页面交接

- 保存成功后由 A 发出 SSE 通知：`{"type":"draft_saved","operation_id":"op_001","version":1}`，首次创建和编辑共用；不依赖模型生成。
- 页面按 `operation_id` 读取当前草稿，返回字段为 `operation_id`、`version`、`status`、`source_message_id`、`thread_id`、`to`、`subject`、`body`。
- 刷新时按 `task_id` 查询，返回 `{"task_id":"task_001","operations":[{"operation_id":"op_001","version":1,"status":"pending"}]}`；无操作时列表为空，已发送操作仍保留。
- 页面依据服务端内容和对应版本展示、编辑及确认。具体 HTTP 路径由 A 实现时确定。

## 8. 用户确认发送

用户明确点击“确认发送”时，页面提交操作 ID 和正在审阅的已保存版本：

```json
{
  "operation_id": "op_001",
  "version": 2
}
```

A 的 Confirmation 依次负责：

1. 校验登录用户身份。
2. 检查当前版本是否与请求版本一致，以及操作状态是否允许执行。
3. 原子记录对应版本的确认并取得执行权，防止重复点击导致重复发送。
4. 读取服务端保存的已确认版本内容，调用 B 的发送函数。

页面存在尚未保存的修改时，先保存并展示保存后的版本，再允许确认。发送内容始终来自用户明确确认的已保存版本，不从确认请求另行接收邮件正文，也不让模型重新生成发送参数。

## 9. 发送邮件回复

提供方：B。调用方：A 的 Confirmation。内部方法暂名 `send_reply`，不暴露给模型。

| 输入字段 | 用途 |
| --- | --- |
| `operation_id`、`version` | 标识此次执行对应的操作及确认版本 |
| `source_message_id`、`thread_id` | 定位原邮件及线程 |
| `to`、`subject`、`body` | 服务端保存的已确认收件人、主题和正文 |

- A 校验确认、取得执行权并读取对应版本，然后调用发送函数。
- B 将已确认内容转换为 Gmail 请求并发送，返回实际结果；不重新生成或修改收件人、主题和正文。
- Gmail 协议所需的回复关联信息由 B 负责处理，具体细节由 B 验证。
- A 将执行结果关联到此次操作和版本，保存后展示。

### 发送结果

| `status` | 含义 | 其他字段 |
| --- | --- | --- |
| `sent` | 已确认发送成功 | `message_id`：Gmail 返回的已发送邮件 ID |
| `failed` | 明确未发送成功 | `reason`：实际失败原因 |
| `unknown` | 暂时无法确定是否已发送 | `reason`：不确定的原因 |

发送超时不能直接归为 `failed`，因为邮件可能已经发出。`unknown` 必须先由 B 核实实际结果，不能直接重发。此处描述邮件发送结果，与第 3 节 Agent 本轮运行的 `done` / `error` 事件分开。

核实方式待 B 验证；不预设自动轮询或重试机制。

## 10. 执行结果交回 Agent

1. A 先保存实际发送结果，关联到对应操作和版本。
2. A 根据任务找到原 SDK 会话。
3. A 将操作 ID、版本和发送结果交给 B，由 B 将结果送回原 Agent 会话。
4. B 继续通过第 3 节约定的事件流返回 Agent 回复，依据实际结果说明执行情况。

结果内容示例：

```json
{
  "operation_id": "op_001",
  "version": 2,
  "result": {
    "status": "sent",
    "message_id": "gmail_789"
  }
}
```

结果必须先保存，再交给 Agent；即使 Agent 的后续回复失败，页面仍能显示真实发送结果，不能据此将邮件发送结果改为失败。

## 11. 回复操作状态

| 状态 | 含义 |
| --- | --- |
| `pending` | 草稿已保存，等待用户确认，可编辑 |
| `sending` | 已确认并取得执行权，正在发送，不可编辑 |
| `sent` | 已发送成功 |
| `failed` | 明确发送失败 |
| `unknown` | 发送结果待核实 |

正常流转：`pending` → 用户确认 → `sending` → `sent` / `failed` / `unknown`。

编辑待确认草稿时增加版本，状态仍为 `pending`。同一版本的重复确认只返回已有状态，不再次调用发送函数；例如已进入 `sending` 后再次确认，返回正在发送。

明确失败后如何由用户再次发起操作，另行确定；不增加自动重试。

## 12. 联调前待核对

- B 验证 SDK 会话恢复、事件返回及执行结果交回原会话的可行性。
- B 验证 Gmail 回复所需协议字段、校验规则及发送结果核实方式。
- 双方确定方法名、保存与编辑的错误返回结构，以及跨任务复用操作时的关联方式。
- 明确发送失败后的用户再次操作方式；当前不约定自动重试。
